# Backend: Rust + PostgreSQL

Сервер заменил прежнее хранилище в браузере (localStorage). Он написан на Rust целиком, данные лежат в PostgreSQL 16, права и правила статусов проверяются на сервере и дополнительно в самой БД.

```
Браузер (React)  ──  POST /graphql, GET /media/photos/{id}  ──▶  Rust (axum + async-graphql)  ──▶  PostgreSQL 16
   HttpOnly-cookie                                                argon2id · JWT · роли · аудит         ограничения · триггеры · bytea
```

## Запуск

Нужны [Rust](https://rustup.rs) (актуальный stable; проверено на 1.97) и PostgreSQL 16. Самый простой способ получить PostgreSQL — Docker:

```bash
docker compose up -d db          # PostgreSQL 16 на 127.0.0.1:5432, пользователь и база volontiers
```

Без Docker поставьте PostgreSQL 16 обычным установщиком и создайте пользователя и базу `volontiers` (пароль `volontiers_dev`) — или поменяйте `DATABASE_URL` в `backend/.env`.

```bash
cd backend
cp .env.example .env             # на Windows PowerShell: Copy-Item .env.example .env
cargo run -- seed                # применяет миграции и загружает демо-данные
cargo run                        # сервер на http://127.0.0.1:8080
```

Во втором окне терминала запустите фронтенд (в корне репозитория):

```bash
npm install
npm run dev                      # http://localhost:3000, запросы /graphql и /media идут на сервер через прокси Vite
```

Одним сервером (без Vite): `npm run build`, затем в `backend/.env` оставьте `STATIC_DIR=../dist` — Rust-сервер сам отдаёт собранный фронтенд на http://127.0.0.1:8080.

Команды сервера: `serve` (по умолчанию), `migrate`, `seed [--reset]`, `create-admin <email> <Фамилия> <Имя>`, `purge-audit <дней>` (удаляет записи журнала старше срока; не менее 365 дней; выполняется от владельца БД), `schema`.

## Модель данных

Основа — схема из задания. Агрегаты и названия сохранены:

| В задании | Таблица | Поля |
|---|---|---|
| Person (firstName, lastName, birthDate) | `persons` | `first_name`, `last_name`, `birth_date` (+ `middle_name`) |
| Organization (name, eventList) | `organizations` | `name`, контакты; события — `events.organization_id` |
| Event (organization, startDateTime, endDateTime, description) | `events` | `organization_id`, `start_at`, `end_at`, `description` (+ название, место, часы, число волонтёров) |
| Volonteer (person, eventBookingList) | `volonteers` | `person_id`; заявки — `volonteer_event_requests.volonteer_id` |
| VolonteerEventRequest (description, event, volonteer) | `volonteer_event_requests` | `description`, `event_id`, `volonteer_id` (+ часы, причина отказа) |

**Статусы** — как на картинке, и БД сама не даёт нарушить порядок (триггеры):

- Event: `DRAFT → CANCELLED | ACCEPTED → CLOSED | CANCELLED`
- Request: `OPEN → CANCELLED | ACCEPTED → CONFIRMED | CANCELLED`

Стрелки `ACCEPTED → CANCELLED` добавлены по решению заказчика (Q2). Отмена принятого события каскадом отменяет его заявки в `OPEN` и `ACCEPTED` (триггер, причина — `events.cancel_reason` или стандартный текст); если у события уже есть заявка `CONFIRMED`, отмена отклоняется. Принятую заявку можно отменить, пока событие в статусе `ACCEPTED` (отмену делает организатор или сам волонтёр).

Остальные правила на уровне БД: заявка создаётся только на событие `ACCEPTED`; одна заявка на пару (волонтёр, событие); `confirmed_hours` есть тогда и только тогда, когда статус `CONFIRMED`; отзыв — только участника (заявка `CONFIRMED` либо `ACCEPTED` на `CLOSED`-событии), один на участника, оценка 1–5, текст 10–1000 символов; не более 5 фото у метки, и только у меток ПСО; закрытое событие нельзя редактировать.

**Дополнения к картинке** (в задании их не было, но без них не работают вход, отзывы и карта): `users` (учётные записи, связаны с `persons` и с организацией или волонтёром), `event_reviews`, `map_markers`, `photos` (изображения в `bytea`), `marker_closures` (отчёты о закрытии ПСО), `audit_log` (журнал действий, только добавление). В `users` хранятся `consent_version`, `consent_at` (согласие 152-ФЗ; оба поля либо пусты, либо заполнены) и `deleted_at` (учётная запись удалена и обезличена).

**Метки ПСО.** Когда администратор согласовывает закрытие ПСО, метка удаляется целиком: фото и отчёт — каскадом, ответ API содержит снимок метки. Статусов `FOUND`/`CLOSED` у ПСО в базе не остаётся.

Московское время: даты событий приходят и уходят как `ГГГГ-ММ-ДД` (по Москве) для фронтенда; в БД лежат `timestamptz` (`startDateTime`/`endDateTime` в API — RFC 3339).

## API и права по ролям

GraphQL, один эндпоинт `POST /graphql`. Права проверяет сервер; кнопки в интерфейсе — лишь удобство.

| Действие | Гость | Волонтёр | Организатор | Админ |
|---|:-:|:-:|:-:|:-:|
| События `ACCEPTED`/`CLOSED`, отзывы, карта | ✓ | ✓ | ✓ | ✓ |
| Черновики и отклонённые события | — | — | свои | все |
| Контакты организации | — | — | своей | все |
| Заявки | — | свои | на свои события | все |
| Данные волонтёров | — | свои | имя, факультет, билет, email, телефон — у тех, кто подал заявку на их события | все |
| Дата рождения | — | своя | — | все |
| Создать событие | — | — | для своей организации | для любой |
| Согласовать/отклонить событие | — | — | — | ✓ |
| Отменить событие (`DRAFT` или `ACCEPTED`) | — | — | свои | ✓ |
| Принять/отклонить/отозвать заявку, подтвердить часы, закрыть событие | — | — | свои события | ✓ |
| Подать заявку, отказаться (`OPEN` или `ACCEPTED`) | — | за себя | — | за любого |
| Оставить отзыв | — | за себя, после участия | — | за любого |
| Удалить отзыв | — | свой | — | ✓ |
| Поставить метку | — | ✓ | ✓ | ✓ |
| Фото-отчёт о закрытии ПСО | — | ✓ | ✓ | ✓ |
| Согласовать/отклонить закрытие ПСО, удалить метку | — | — | — | ✓ |
| Список учётных записей, регистрация организаций и волонтёров | — | — | — | ✓ |
| Выгрузить свои данные (`exportMyData`), удалить аккаунт (`deleteMyAccount`) | — | ✓ | ✓ (если нет принятых событий) | — (самоудаление запрещено) |

Администратор может действовать «от имени» любой организации или волонтёра — так в демо работает переключатель профилей. Каждое такое действие пишется в журнал аудита с id администратора.

## Безопасность данных

Что защищаем: персональные данные пользователей (ФИО, email, телефон, дата рождения, номер студенческого билета), данные поисково-спасательных операций (фотографии людей, в том числе детей и пожилых, описания, координаты, телефоны), данные для входа, а также подтверждённые часы, которые идут в справки и стипендию.

### Авторизация и сессии

- Пароль хранится только как хэш **Argon2id** со случайной солью. Политика: 8–128 символов, буквы и цифра или спецсимвол, не из списка простых.
- Вход выдаёт **JWT (HS256)** на 24 часа. Для браузера он лежит в cookie `vt_session` с флагами `HttpOnly` (скрипты страницы токен не видят, это снижает ущерб от XSS), `SameSite=Lax` и `Secure` (в production). В теле ответа токена нет; не-браузерным клиентам он выдаётся по заголовку `X-Token-Response: 1` и принимается как `Authorization: Bearer`.
- В токене хранятся только id пользователя и версия токена. Роль и привязки сервер каждый раз берёт из БД, поэтому смена роли действует сразу.
- **Выход и смена пароля отзывают все сессии** (растёт `token_version`).
- После **5 неверных паролей** учётная запись блокируется на 15 минут. Для несуществующего email и неверного пароля — одинаковое сообщение, и одинаковое время ответа (тратится такой же argon2), поэтому перебор адресов не работает. Ограничитель частоты по IP: вход 20, регистрация 10 в минуту (в памяти процесса, при нескольких копиях сервера нужен общий лимитер на прокси).
- Публичная регистрация создаёт только волонтёров и организаторов (Q3: организатор регистрируется сам и указывает название организации; без названия создаётся «Организация: Фамилия Имя»). Регистрация требует `consent: true`, иначе отказ. Администратор создаётся командой `create-admin`; демо-сид в production запрещён.
- **CSRF**: запросы с чужим заголовком `Origin` отклоняются (разрешённые источники — `ALLOWED_ORIGINS`); `SameSite=Lax` — вторая линия.

### Персональные данные

- **Минимум по ролям** (см. матрицу выше): гость не получает ни заявок, ни контактов, ни дат рождения; волонтёр видит только себя; организатор — только тех, кто подал заявку на его события, и без даты рождения. Отзывы публичны, но автор показывается только ФИО.
- Пределы длин и диапазонов проверяются и в коде, и в БД (`CHECK`); управляющие символы в текстовых полях отсекает код.
- **Журнал аудита** (`audit_log`): входы (успешные и неудачные), блокировки, регистрации, создание и смена статусов событий и заявок, подтверждение часов, отзывы, действия с метками и фото. Записи нельзя изменить или удалить (триггеры), рабочая роль БД вправе только добавлять. Пароли, токены и тексты отзывов в журнал не попадают.
- Логи сервера не содержат тел запросов.
- **152-ФЗ** (подробнее — [PRIVACY.md](PRIVACY.md)):
  - *Согласие.* Регистрация без согласия отклоняется; сервер хранит версию политики (`privacyPolicyVersion`) и время согласия.
  - *Выгрузка.* Мутация `exportMyData` возвращает JSON со всеми данными пользователя: профиль, заявки, отзывы, метки и журнал его действий.
  - *Удаление.* Мутация `deleteMyAccount(password)` обезличивает ФИО, почту, телефон, студенческий билет и дату рождения, удаляет отзывы, отменяет активные заявки, обезличивает метки и отчёты пользователя, отзывает сессии и блокирует вход. Подтверждённые часы остаются без имени для отчётности организатора. Администратор и организатор с принятыми событиями удалить аккаунт не могут.
  - *Хранение.* Журнал аудита хранится 3 года; чистит его `purge-audit`. Закрытые ПСО удаляются сразу.
- **Не сделано** (в бэклоге): подтверждение email, срок хранения неактивных аккаунтов, шифрование полей, реквизиты оператора.

### Фотографии

- Фото хранятся **в PostgreSQL** (`photos.data`), а не на диске: они попадают в тот же бэкап, на них действуют те же права и транзакции — метка и её фото создаются атомарно.
- Принимается только изображение: сигнатура JPEG/PNG/WebP, до 6 МБ на файл, до 5 фото на метку, не больше 8000×8000 пикселей при декодировании. Сервер **полностью декодирует и заново кодирует** снимок в JPEG (до 1600 пикселей, качество 82): так пропадают EXIF и GPS-координаты, встроенные скрипты и файлы-«полиглоты».
- Отдача только через `GET /media/photos/{uuid}` (идентификаторы случайные, угадать нельзя) с заголовками `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-site`, `ETag`.
- Фото метки ПСО публичны, пока `PUBLIC_MARKER_PHOTOS=true` (так листовка о пропавшем человеке работает по назначению); при `false` — только для вошедших. **Фото-отчёты о закрытии ПСО** (найденный человек) всегда только для вошедших и не кэшируются публично.
- Фото к обычным меткам не принимаются. Удаление метки удаляет её фото каскадом; закрытая ПСО удаляется вместе с фото и отчётом сразу. Фото публикуются без предварительной модерации.

### Карта

- Координаты и описания меток — данные о конкретных людях и местах, поэтому ставить метки могут только вошедшие, а согласовывает закрытие ПСО администратор. Метка ПСО не закрывается без фото-отчёта.
- Закрыть обычную метку может её автор или администратор; метки ПСО — только через отчёт.
- Отчёты о закрытии (заметка, фото, кто подал, кто согласовал) скрыты от гостей.
- Тайлы карты грузятся с серверов OpenStreetMap: их владелец видит IP и область просмотра пользователя (см. бэклог про собственный тайл-сервер).

### База данных

- Две роли: `volontiers_owner` (миграции) и `volontiers_app` (только `SELECT/INSERT/UPDATE/DELETE`, без DDL и `TRUNCATE`, в журнале аудита — только чтение и добавление). Сервер в production работает под `volontiers_app` (`RUN_MIGRATIONS=false`).
- Допустимость статусов, уникальность, числовые и текстовые пределы, привязка пользователя к роли (`ORGANIZER` ⇒ есть организация, `VOLUNTEER` ⇒ есть профиль волонтёра) гарантирует БД, даже если ошибся код.
- Все изменения идут в транзакциях; переходы статусов — атомарным `UPDATE … WHERE status = $из`, поэтому гонки (двойное подтверждение часов, две заявки одновременно) не ломают данные; повторное подтверждение часов отклоняется.
- Соединение с PostgreSQL по сети — с `sslmode=verify-full` (TLS через rustls включён; проверено с `sslmode=require`).
- Журнал защищён от изменений триггерами, но не от администратора БД: владелец схемы может их удалить. Для настоящей неизменяемости журнал нужно выгружать во внешнее хранилище (бэклог).
- Резервные копии (`pg_dump` по расписанию, шифрование и проверка восстановления) и шифрование диска — на стороне эксплуатации, в проект не входят.

### Транспорт и сервер

- GraphQL: глубина запроса не более 8, сложность не более 600, **интроспекция выключена в production**, пакетные запросы не принимаются; тело запроса ограничено (по умолчанию 16 МБ).
- Все ответы `/graphql` — `Cache-Control: no-store`. Заголовки: `Content-Security-Policy` (скрипты только свои), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy`.
- Внутренние ошибки клиенту не раскрываются: он получает общий текст, подробности — в лог сервера.
- HTTPS и HSTS обеспечивает reverse proxy (nginx/Caddy); сервер слушает локальный адрес.

## Развёртывание в production

1. Создайте роли и базу: `psql -f backend/db/init-roles.sql` (замените пароли).
2. Миграции от владельца: `DATABASE_URL=…volontiers_owner… cargo run --release -- migrate`.
3. Переменные сервера: `APP_ENV=production`, `DATABASE_URL` с ролью `volontiers_app` и `sslmode=verify-full`, `JWT_SECRET` (`openssl rand -hex 32`), `ALLOWED_ORIGINS=https://ваш-домен`, `RUN_MIGRATIONS=false`, `TRUST_PROXY=true` за nginx/Caddy, при необходимости `PUBLIC_MARKER_PHOTOS=false`.
4. Администратор: `ADMIN_PASSWORD='…' cargo run --release -- create-admin admin@вашдомен.ru Фамилия Имя`.
5. Собранный фронтенд (`npm run build`) — через `STATIC_DIR` либо nginx; перед сервером обязателен HTTPS.
6. Настройте резервное копирование и мониторинг (`GET /healthz`).

Отдельный тест сверяет `schema.graphql` с кодом.

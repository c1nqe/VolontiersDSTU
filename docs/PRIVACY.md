# Обработка персональных данных

Версия политики: **2026-10-09** (константа `PRIVACY_POLICY_VERSION` в `backend/src/svc.rs`; сервер отдаёт её запросом `privacyPolicyVersion`). Краткий текст для пользователей показывается при регистрации и в личном кабинете (`src/components/PrivacyPolicy.jsx`); этот документ — полная редакция для разработчиков и юристов.

> **Статус.** Черновик, подготовленный разработчиками на основании решений заказчика от 9 октября 2026 г. (Q6: требования 152-ФЗ нужны). Перед запуском для реальных пользователей его должен проверить юрист университета. Оператор персональных данных пока **не указан** — реквизиты нужно вписать при выходе в эксплуатацию.

## 1. Оператор

## 2. Какие данные обрабатываются

| Категория | Данные | Кто вводит |
|---|---|---|
| Учётная запись | Имя, фамилия, электронная почта, пароль (хранится только как хэш Argon2id) | Пользователь при регистрации |
| Профиль волонтёра | Номер студенческого билета, факультет, телефон, дата рождения | Администратор (самостоятельно зарегистрированные волонтёры их не заполняют) |
| Профиль организации | Название, контактное лицо, почта, телефон, ИНН, описание | Организатор или администратор |
| Деятельность | Заявки на мероприятия, подтверждённые часы, отзывы | Пользователь, организатор |
| Карта | Метки (описание, координаты, телефон для связи), фотографии ПСО, фото-отчёты о закрытии | Пользователь |
| Журнал действий | Время, действие, идентификаторы объектов; без паролей, токенов и текстов сообщений | Сервер автоматически |
| Согласие | Версия политики и время согласия | Сервер при регистрации |

Специальные категории данных и биометрия не запрашиваются. Фотографии на метках ПСО могут изображать третьих лиц (пропавших людей): их размещают те, кто ставит метку, ответственность за основание размещения — на них и на администраторе, согласующем ПСО.

## 3. Цели

Учёт волонтёрской деятельности: приём и обработка заявок, подтверждение часов, выписка о часах для стипендии и портфолио, отзывы о мероприятиях, координация поисков на карте, защита сервиса (журнал аудита).

## 4. Основание

Согласие субъекта. Регистрация невозможна без отметки согласия: сервер отклоняет запрос `register` с `consent = false` и сохраняет в `users.consent_version` и `users.consent_at` версию политики и время. В базе есть ограничение: оба поля пусты или оба заполнены.

## 5. Кто видит данные

| Данные | Гость | Волонтёр | Организатор | Администратор |
|---|:-:|:-:|:-:|:-:|
| Согласованные мероприятия, отзывы (автор — только ФИО) | ✓ | ✓ | ✓ | ✓ |
| Метки карты и их фото | ✓ (фото — пока `PUBLIC_MARKER_PHOTOS=true`) | ✓ | ✓ | ✓ |
| Фото-отчёты о закрытии ПСО | — | ✓ | ✓ | ✓ |
| Имя, факультет, билет, почта, телефон волонтёра | — | свои | только тех, кто подал заявку на его события | все |
| Дата рождения | — | своя | — | все |
| Контакты организации | — | — | своей | все |

Решение Q1: фотографии ПСО показываются гостям, чтобы ориентировка работала по назначению. При необходимости это отключается настройкой `PUBLIC_MARKER_PHOTOS=false`.

Данные не передаются третьим лицам. Исключение — внешние сервисы, к которым обращается браузер: плитки карты OpenStreetMap и шрифты Google Fonts видят IP-адрес пользователя (в бэклоге: B-08).

## 6. Сроки хранения

| Данные | Срок |
|---|---|
| Учётная запись и профиль | До удаления аккаунта пользователем. Срок хранения неактивных аккаунтов не определён (бэклог B-14) |
| Закрытая ПСО (метка, фото, отчёт) | Удаляется сразу после согласованного закрытия (Q7) |
| Обычная метка | До удаления; закрытая обычная метка остаётся со статусом `CLOSED` |
| Журнал аудита | 3 года, затем удаляется командой `purge-audit` |
| Подтверждённые часы после удаления аккаунта | Остаются у организатора без имени, для отчётности |

## 7. Права субъекта и как они реализованы

| Право | Как реализовано |
|---|---|
| Доступ к данным | Личный кабинет → «Скачать мои данные». Мутация `exportMyData` отдаёт JSON: учётная запись, профиль волонтёра, организация, заявки, отзывы, метки (с числом загруженных фото), журнал действий (до 1000 последних записей). Сама выгрузка пишется в журнал |
| Удаление | Личный кабинет → «Удалить аккаунт», подтверждение паролем. Мутация `deleteMyAccount` в одной транзакции: обезличивает имя, почту, телефон, билет, факультет и дату рождения; удаляет отзывы; отменяет активные заявки; обезличивает метки и отчёты пользователя; отзывает все сессии и блокирует вход |
| Отзыв согласия | Равнозначен удалению аккаунта |
| Исправление | Через администратора; экран редактирования профиля в бэклоге (F-07) |

Ограничения удаления:

- Администратор не может удалить аккаунт сам (иначе можно потерять доступ к управлению).
- Организатор с принятыми (`ACCEPTED`) событиями не может удалить аккаунт: сначала нужно отменить или закрыть события (бэклог B-15).
- Контакты организации очищаются, если в ней не осталось других пользователей.
- Запись в таблице `users` остаётся как «надгробие» (удалённый пользователь без персональных данных), чтобы не нарушить целостность журнала и подтверждённых часов.

## 8. Защита

Технические меры описаны в [BACKEND.md](BACKEND.md#безопасность-данных): Argon2id, HttpOnly-сессии, проверка прав на сервере и в БД, перекодирование фото без EXIF и GPS, журнал аудита без возможности правки, минимальные права рабочей роли БД. Резервные копии и шифрование диска — на стороне эксплуатации.

## 9. Что нужно сделать до запуска

1. Указать оператора и контакт ответственного (раздел 1) и подать уведомление Роскомнадзора.
2. Проверить текст у юриста университета, в том числе размещение фото третьих лиц и хранение обезличенных часов.
3. Определить срок хранения неактивных аккаунтов (B-14).
4. Выбрать место развёртывания: серверы для баз данных граждан РФ должны находиться на территории РФ (Q5).
5. Настроить регулярный запуск `purge-audit 1095` (3 года) под ролью владельца БД.
6. При изменении текста — повысить `PRIVACY_POLICY_VERSION`.
